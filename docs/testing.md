# Test strategy

The hardening phase adds production config rejection/strict TLS tests, Secure-cookie assertions, broker reconnect coverage, and `npm run test:hardening`. The latter creates dedicated test databases/roles, checks restricted grants through actual HTTP transfers, runs the worker and protected metrics, and verifies an encrypted backup/restore by table digests and ledger constraints. PostgreSQL test containers and built API are prerequisites; the existing demo is not reset. Test databases/roles remain for inspection.

`node scripts/tls-check.mjs` tests the Caddy edge with a local CA and diagnostic upstream on ports 8443/8085/3103. `node scripts/database-tls-check.mjs` tests PostgreSQL TLS and privileged-role startup rejection in a new temporary container on port 55434; it needs the existing `finledger-api` tools image for OpenSSL. Both require Docker and stop only their own ephemeral containers. They do not contact public ACME or deploy staging. Current results are in `PRODUCTION_READINESS_REPORT.md` and `docs/*-results.json`.

Unit tests verify exact monetary bounds, invalid decimal inputs and formatting beyond JavaScript safe integers. Integration tests instantiate the actual Nest application and use Supertest with real PostgreSQL transactions. RabbitMQ tests use the actual broker, confirmations, retry queue TTL and dead-letter routing. Only fault injection (forced storage/consumer failures) uses test hooks; money operations are not mocked.

`docker compose --profile test up -d --wait postgres-test redis rabbitmq` starts isolated local services. `npm run db:test` migrates only `TEST_DATABASE_URL`; its database name must end in `_test`. Tests create unique users and keep append-only history rather than weakening production immutability to clean fixtures. The disposable test PostgreSQL container uses tmpfs. Recreate only that container to reset it; never aim tests at the development database.

Coverage includes registration, wrong credentials, protected routes, refresh rotation, replay revocation, logout, role checks, origin rejection, cross-user detail denial, source ownership, missing destinations, self-transfers, invalid amounts, insufficient funds, idempotent replay and conflicts. A trigger injects an outbox write failure inside the money transaction; the test verifies rollback and retries the original key successfully after removal.

The concurrency suite sends 50 simultaneous HTTP transfers from a wallet holding 1000 minor units, each spending 100. Exactly 10 may succeed; 40 must fail for insufficient funds. It verifies no overdraft, unique effects, recipient increase, total zero-sum money and every journal/cache. Another test submits 20 simultaneous copies of the same key. Concurrent funding verifies the PostgreSQL quota.

Browser E2E covers registration, wallet creation, funding, transfer, ledger details, session renewal, mobile overflow, clipboard copying, history filtering, profile, logout and login errors. Additional cases exercise the real admin APIs and inject lost funding responses and refresh outages to verify recovery. Playwright starts a built API against the isolated test database on port 3100 and Vite on 8180. Test rate-limit namespaces and broker queues are isolated per run. `E2E_EXTERNAL=1` uses an already running stack; set `E2E_URL` to its origin. External tests create demo data; test-only admin provisioning is skipped.

Regression integration tests also cover malformed/expired JWTs, registration rollback, reversed date ranges, all admin route permissions, notification ownership, unroutable broker messages and invalid retry headers. Tests do not claim exhaustive browser, load or failure-interleaving coverage. See [GitHub readiness](../GITHUB_READINESS_REPORT.md) for the latest executed counts and exclusions.

The load script creates two disposable accounts, funds one and submits 50 parallel requests. It records actual elapsed time, throughput, p50/p95/max latency and HTTP status counts to `docs/load-results.json`. Expected insufficient-funds responses are business rejections, not unexpected errors. This is a small local contention test, not a production capacity benchmark. Run under reproducible hardware/container conditions; avoid comparing results taken during image builds.

For isolated load verification after building, run `node scripts/test-load.mjs`. It starts the built API on port 3101 with `TEST_DATABASE_URL`, executes the load and ledger integrity scripts, and stops that API. It does not replace the running demo or reset a database. Results overwrite `docs/load-results.json` with the measured environment and timestamp.

CI uses newly generated random credentials and isolated Docker services per runner. It checks formatting, lint, types, unit/integration/browser tests, production builds and Docker startup. Actual local evidence is kept in `verification.md`; a workflow file alone does not imply a successful remote GitHub run.
